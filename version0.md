# 1. Overview

This document describes how to operate the H2GCROC test setup based on a Xilinx KCU105 FPGA board.

The setup currently supports:

- Firmware writing to the KCU105
- Communication with the KCU105
- Configuration of the H2GCROC
- H2GCROC calibration procedures
- Internal trigger operation
- External trigger input
- Data acquisition using RCDAQ
- Online monitoring using `pmonitor` and `roc_analysis`

The typical system configuration is:

```text
                         +------------------+
                         |  Pulse Generator |
                         |  / Trigger Logic |
                         +---------+--------+
                                   |
                                   | External Trigger
                                   v
+----------------+        +--------+--------+        +----------------+
|                |        |                 |        |                |
|    H2GCROC     +<------>+     KCU105      +<------>+    DAQ PC      |
|                |        |                 |  UDP   |                |
+-------+--------+        +-----------------+        +----------------+
        |
        |
        v
   SiPM / detector
```

The KCU105 communicates with the H2GCROC and transfers event data to the DAQ computer through Ethernet/UDP.

The connection can be made using:

- 1 Gbps Ethernet through the RJ45 port
- 10 Gbps Ethernet through the SFP+ port

The 10 Gbps connection from the upper SFP+ slot is recommended for high-rate operation.

# 2. Hardware

## 2.1 Required hardware

The basic setup consists of:

- Xilinx KCU105 evaluation board
- H2GCROC mezzanine board
  - Several versions exist.
  - The current setup uses the ALICE FoCal-type mezzanine with one H2GCROC ASIC on one carrier board.
- H2GCROC ASIC
- Ethernet connection between the KCU105 and DAQ PC
- Power supplies required by the H2GCROC setup
- External trigger source, if required
- SiPMs and scintillators for detector tests
  - These are not required for basic ASIC calibration.

# 5. Network Setup

The KCU105 communicates with the DAQ PC through Ethernet using UDP.

Before starting any calibration or DAQ software, verify that the KCU105 is reachable from the DAQ computer.

For example:

```bash
ping -s 32 10.1.2.208
```

A successful response confirms basic IP-level communication.

Note that successful `ping` communication does **not** guarantee that UDP communication is working correctly.

---

## 5.1 Firewall

The firewall can block UDP communication even when `ping` works correctly.

If the software can send commands to the KCU105 but does not receive replies or event packets, check the firewall configuration.

A host firewall has previously caused the H2GCROC software to freeze while waiting for UDP replies.

If necessary:

- allow the required UDP traffic explicitly;
- or temporarily disable the firewall for debugging.

Do not permanently disable the firewall without understanding the network environment.

# 6. H2GCROC Configuration

After communication with the KCU105 has been established, start the H2GCROC calibration software.

Follow the instructions in the software README.

For the current single-ASIC test setup:

```text
number_of_asic = 1
```

Do not use a configuration intended for four ASICs when only one ASIC is connected.

A mismatch in `number_of_asic` can cause incorrect packet handling or software behavior.

## 6.1 Analog front-end parameters

Several parameters control the H2GCROC analog front end.

Important parameters include:

- `Rf`
- `Cf`
- `Cf_comp`
- `Cd`
- `gain_conv`

`Rf`, `Cf`, and `Cf_comp` have programmable settings from 0 to 15. Some extreme configurations may not provide useful analog behavior.

A commonly used configuration is:

```text
Cf        = 1010
Cf_comp   = 1010
Rf        = 1100
Cd        = 0
gain_conv = 1100
```

With the detector configuration for which these defaults were developed, the MIP peak is approximately 15 ADC counts.

The optimal configuration depends on:

- SiPM capacitance
- required ADC gain
- required dynamic range
- noise level
- MIP signal size

Therefore, the analog configuration should be validated with an injection linearity scan before detector operation.

# 7. Basic Calibration Procedure

The following calibration procedures should normally be performed before detector data taking.

A typical calibration sequence is:

```text
IOdelayY
   ↓
PedestalCalibY
   ↓
InjectionY
   ↓
TOA / TOT calibration
   ↓
InjectionDACY / linearity scan
```

The exact sequence may depend on the firmware and calibration software version.

---

## 7.0 IO Delay Scan: `IOdelayY`

`IOdelayY` aligns the digital communication timing between the H2GCROC and the FPGA.

This calibration is fundamentally different from the later injection timing calibration.

Its purpose is to find a stable digital sampling point for communication between the ASIC and FPGA.

An incorrect I/O delay can result in:

- corrupted data;
- missing data;
- unstable register communication;
- apparently random decoding errors.

Therefore, the I/O delay scan should be performed before the other H2GCROC calibration procedures.

Conceptually:

```text
ASIC digital output
       |
       | scan FPGA sampling delay
       v
Find stable timing window
       |
       v
Choose working IO delay
```

---

## 7.1 Pedestal Calibration: `PedestalCalibY`

The pedestal calibration determines and equalizes the baseline ADC values.

Two important register parameters are adjusted to move the pedestal to the target ADC value and reduce channel-to-channel variations.

### `Inv Vref`

`Inv Vref` controls the global pedestal position for each half of the ASIC.

It provides a relatively coarse adjustment shared by a group of channels.

The calibration first adjusts `Inv Vref` so that the pedestal is close to the requested target ADC value.

### `Chn Trim Inv`

`Chn Trim Inv` provides a per-channel pedestal correction.

After the global pedestal level has been adjusted with `Inv Vref`, the individual channels are fine-tuned using `Chn Trim Inv`.

Conceptually:

```text
Target pedestal
      |
      v
Adjust Inv Vref
(global / half-chip)
      |
      v
Adjust Chn Trim Inv
(channel-by-channel)
      |
      v
Uniform pedestal distribution
```

`PedestalCalibY` performs this pedestal equalization automatically.

After calibration, always verify the resulting pedestal distribution.

Check for:

- channels with abnormal pedestal values;
- channels close to the ADC boundaries;
- channels requiring unusually large trim corrections;
- large residual channel-to-channel variations.

The output configuration generated by this procedure should be used as the input configuration for subsequent calibrations.

---

## 7.2 Injection Phase Calibration: `InjectionY`

`InjectionY` is used to determine the appropriate **timing phase of the internal charge injection relative to the H2GCROC sampling clock**.

It should not be confused with `InjectionDACY`.

The distinction is:

```text
InjectionY
    -> scan WHEN the charge is injected

InjectionDACY
    -> scan HOW MUCH charge is injected
```

During `InjectionY`, a fixed calibration charge is injected while the relative injection phase is scanned.

The ADC response changes because the H2GCROC samples the shaped analog pulse at a fixed clock timing.

Conceptually:

```text
Injected pulse
     /\
    /  \
---/----\---------------- time
   ^    ^
   |    |
different sampling phases
```

If the sample is taken too early or too late, the measured ADC value is smaller.

The phase giving the largest ADC response corresponds approximately to sampling near the maximum of the shaped pulse.

The procedure is therefore:

```text
Fixed injection DAC
       |
       v
Scan injection phase
       |
       v
Measure ADC response
       |
       v
Find phase with maximum response
       |
       v
Use this phase for later injection scans
```

In the present setup, one 25 ns clock period can be divided into fine phase settings. For a 16-step phase scan, the nominal phase spacing is:

```text
25 ns / 16 = 1.5625 ns
```

This **1.56 ns is the injection-phase scan step**, not the intrinsic TOA resolution of the ASIC.

### What to check

The result should show a recognizable pulse shape as a function of the injection phase.

Check that:

- the ADC response varies smoothly with phase;
- a clear maximum can be identified;
- all expected phase values are present;
- the selected phase is not unexpectedly located at a scan boundary.

If one phase is systematically missing, for example phase 15, first check the calibration software scan loop and FPGA configuration before interpreting the effect as an ASIC problem.

---

## 7.3 TOA and TOT Calibration

H2GCROC provides two timing-related quantities:

- **TOA — Time of Arrival**
- **TOT — Time over Threshold**

Although both use discriminator/TDC circuitry, they serve different purposes.

---

### 7.3.1 TOA: Time of Arrival

TOA measures the timing at which the signal crosses a fast discriminator threshold.

Conceptually:

```text
Signal
       /\
      /  \
-----/----\--------------
    ^
    |
 TOA threshold crossing
```

TOA is therefore mainly a **signal timing measurement**.

The measured time depends on the pulse amplitude because a larger pulse usually crosses the threshold earlier. This effect is known as **time walk**.

The TOA calibration is used to equalize and configure the discriminator thresholds so that the channels respond consistently.

A typical procedure is:

1. Set the global TOA threshold.
2. Inject a fixed charge large enough to cross the TOA threshold.
3. Scan the per-channel TOA threshold trim.
4. Determine an appropriate trim value for each channel.
5. Adjust the global threshold for each chip half if required.
6. Verify that all channels respond consistently.

The TOA calibration therefore primarily calibrates the **TOA discriminator threshold**, rather than the physical TDC time conversion itself.

---

### 7.3.2 TOT: Time over Threshold

TOT measures how long the analog signal remains above the TOT discriminator threshold.

Conceptually:

```text
Signal
             /---------\
            /           \
-----------/-------------\---------
           ^             ^
           |<--- TOT --->|
```

For sufficiently large signals, the H2GCROC preamplifier leaves its normal linear ADC region.

In this region, the duration of the pulse above threshold contains information about the input charge.

TOT therefore provides a charge measurement for larger signals where the normal ADC measurement is no longer sufficient.

The approximate charge-measurement scheme is:

```text
Small / moderate charge
        ↓
       ADC

Large charge / preamplifier saturation
        ↓
       TOT
```

TOT calibration follows a procedure similar to TOA calibration, but normally uses a larger injected charge so that the signal reliably exceeds the TOT threshold.

A typical procedure is:

1. Configure a sufficiently large injection charge.
2. Set the global TOT threshold.
3. Scan the per-channel threshold trims.
4. Determine the appropriate trim value for each channel.
5. Equalize the response of both chip halves.
6. Verify the TOT response using injected charge.

---

### 7.3.3 TOA/TOT thresholds versus Injection DAC

Do not confuse the TOA/TOT threshold DACs with the injection DAC.

They control different quantities:

```text
Injection DAC
    -> amount of calibration charge injected

TOA threshold DAC
    -> discriminator level for TOA

TOT threshold DAC
    -> discriminator level for TOT
```

The injected charge must simply be large enough to cross the corresponding discriminator threshold during calibration.

---

### 7.3.4 Machine Gun

The calibration and DAQ firmware also provides a parameter called `Machine Gun`.

`Machine Gun` specifies how many consecutive samples / fast read commands are generated around one trigger.

It is useful for observing the signal over several BX/sample positions.

Conceptually:

```text
Trigger
   |
   +--> sample 0
   +--> sample 1
   +--> sample 2
   +--> sample 3
   +--> ...
```

This is especially useful for timing studies and for understanding which sample contains the signal peak.

`Machine Gun` is a readout configuration parameter; it is not itself an analog calibration parameter.

---

## 7.4 Linearity Scan: `InjectionDACY`

`InjectionDACY` scans the **internal injection DAC amplitude** while keeping the injection timing approximately fixed.

This is different from `InjectionY`:

```text
InjectionY:
    fixed charge
    scan timing / phase

InjectionDACY:
    fixed timing
    scan injection DAC amplitude
```

The purpose of `InjectionDACY` is to measure the response of the H2GCROC as a function of injected charge.

Conceptually:

```text
Injection DAC
     |
     |  increase
     v

small charge
     ↓
ADC response
     ↓
linear region
     ↓
ADC saturation / transition region
     ↓
TOT region
```

The scan can be used to determine:

- ADC gain;
- ADC linearity;
- usable ADC dynamic range;
- saturation point;
- dependence on `Rf`, `Cf`, and other analog settings;
- TOA response versus charge;
- TOT response versus charge.

For each DAC setting, multiple events should be collected and the average or fitted ADC response should be evaluated.

A typical ADC linearity plot is:

```text
ADC
 ^
 |                ______ saturation
 |              /
 |            /
 |          /
 |        /
 |      /
 |_____/______________________> Injection DAC
```

The linear region can be fitted with:

```text
ADC = pedestal + gain × InjectionDAC
```

where `gain` is expressed in ADC counts per injection-DAC unit.

### Important

The raw injection DAC value should **not automatically be interpreted as physical charge in fC or pC**.

A conversion from injection DAC to physical charge requires the calibration of the internal injection circuit.

Therefore:

```text
Injection DAC code
       !=
physical charge
```

unless a validated DAC-to-charge conversion is available.

When comparing different analog settings such as `Rf` and `Cf`, use the same injection configuration and phase so that the measured differences come from the analog front end rather than timing misalignment.

# 8. Running the DAQ with a Custom Configuration

To run RCDAQ with an optimized H2GCROC configuration:

```text
0. Run IOdelayY using H2GCalibX.
1. Generate/calibrate the ASIC configuration using H2GCalibX.
2. Write the ASIC configuration using H2GConfig.
3. Write the FPGA generator configuration using H2GDAQ.
4. Run RCDAQ.
```

Step 3 may not be required if the nominal FPGA generator configuration is already appropriate.

The three software packages therefore have different roles:

```text
H2GCalibX
     |
     | determine calibration constants
     v
H2GConfig
     |
     | configure ASIC
     v
H2GDAQ
     |
     | configure FPGA generator
     v
RCDAQ
     |
     | acquire physics/test data
     v
pmonitor / roc_analysis
```

# 12. External Trigger Operation

An external trigger can be supplied to the KCU105 through the external-trigger SMA input.

The tested setup is:

```text
Pulse Generator
      |
      v
KCU105 external-trigger SMA
      |
      v
FPGA trigger logic
      |
      v
H2GCROC readout
      |
      v
UDP
      |
      v
RCDAQ
```

The trigger path has been successfully tested with a pulse generator.

---

## 12.1 Electrical level

The relevant SMA connector is labeled for a CMOS-level FPGA input.

The current hardware has been described as a **1.8 V CMOS** input.

However, this should be verified against the KCU105 schematic and FPGA I/O constraints before treating it as a permanent specification.

Do **not** apply a 3.3 V or 5 V trigger signal simply because the signal generator labels it as TTL/CMOS.

Before connecting the pulse generator, check:

- output amplitude;
- DC offset;
- termination mode;
- pulse polarity;
- pulse width;
- FPGA input-voltage limit.

---

## 12.2 External-trigger configuration

In H2GDAQ:

```text
Ext Trg En = enabled
```

must be set.

Configure the trigger delay and dead time as required, and send the generator configuration to the FPGA from H2GDAQ.

After this, RCDAQ can be used to receive data generated by the external trigger.

# 14. Summary of the Complete Setup

The H2GCROC + KCU105 system can be understood as four separate layers:

| Layer | Software / Hardware | Main role |
| --- | --- | --- |
| ASIC | H2GCROC | Amplification, ADC, TOA, TOT, trigger-related processing |
| Front-end control | KCU105 FPGA | ASIC control, trigger handling, charge injection, packet generation |
| Calibration/configuration | H2GCalibX / H2GConfig / H2GDAQ | Determine and write ASIC/FPGA settings |
| Data acquisition | RCDAQ + `roc_analysis` | Receive, record, decode, and monitor events |

The main calibration quantities are:

| Calibration | Scanned quantity | Main purpose |
| --- | --- | --- |
| `IOdelayY` | FPGA/ASIC digital timing | Establish reliable digital communication |
| `PedestalCalibY` | `Inv Vref` + `Chn Trim Inv` | Equalize ADC pedestal |
| `InjectionY` | Injection timing/phase | Find appropriate sampling phase |
| TOA calibration | TOA discriminator settings | Equalize TOA threshold response |
| TOT calibration | TOT discriminator settings | Equalize TOT threshold response |
| `InjectionDACY` | Injection DAC amplitude | Measure gain, linearity, saturation, and dynamic range |

The important distinction is:

```text
IOdelayY
    -> digital communication timing

InjectionY
    -> analog injection/sampling timing

InjectionDACY
    -> injected charge amplitude

TOA
    -> signal arrival timing

TOT
    -> signal duration above threshold / large-signal charge information
```

# 15. Troubleshooting Guide

## 15.1 KCU105 cannot be pinged

Check:

```text
[ ] Ethernet cable
[ ] Correct Ethernet interface
[ ] PC IP address
[ ] KCU105 IP address
[ ] Subnet configuration
[ ] Correct firmware loaded
```

---

## 15.2 `ping` works but H2GCalibX/H2GDAQ does not receive data

The most likely problem is UDP communication.

Check:

```text
[ ] Firewall
[ ] UDP ports
[ ] Network interface
[ ] Correct KCU105 IP
[ ] Correct firmware
```

A firewall can allow ICMP `ping` while blocking the UDP packets required by H2GCROC software.

---

## 15.3 Calibration software freezes while waiting for a reply

Check the firewall first.

Use a packet monitor if necessary:

```bash
tcpdump
```

If outgoing packets are visible but replies never reach the application, check:

- firewall;
- UDP port configuration;
- interface routing.

---

## 15.4 Software reports four ASICs but only one ASIC is connected

Set:

```text
number_of_asic = 1
```

The number of ASICs in the software configuration must match the actual hardware.

---

## 15.5 Pedestal calibration gives abnormal channels

Check:

- `Inv Vref`;
- `Chn Trim Inv`;
- correct ASIC configuration;
- analog front-end configuration;
- whether the channel is saturated at the ADC boundary.

Repeat `PedestalCalibY` after correcting the configuration.

---

## 15.6 `InjectionY` does not show a clear maximum

Possible causes include:

- incorrect injection DAC;
- injection disabled;
- incorrect injection timing range;
- incorrect Machine Gun configuration;
- wrong ADC sample being inspected;
- analog configuration with too little gain.

First verify that the charge injection itself is working.

Then check the full phase scan rather than only one phase.

---

## 15.7 One InjectionY phase is missing

If a phase such as phase 15 is systematically absent:

1. Check whether the software loop actually requests all phase values.
2. Check whether the FPGA accepts the final phase setting.
3. Compare with a neighboring phase.
4. Repeat the scan.
5. Check whether the issue depends on firmware/software version.

Do not immediately interpret a missing phase as an ASIC analog problem.

---

## 15.8 Injection DAC scan is nonlinear

Check the H2GCROC analog settings:

```text
Rf
Cf
Cf_comp
Cd
gain_conv
```

Different front-end configurations can have different gain and saturation behavior.

Also check whether the ADC has already reached its expected nonlinear/saturation region.

A large injected charge may need to be evaluated using TOT rather than ADC.

---

## 15.9 TOA values are missing

Check:

- TOA discriminator threshold;
- injected charge;
- TOA trim calibration;
- injection timing;
- whether the signal actually exceeds the TOA threshold.

A charge that produces a visible ADC signal does not necessarily guarantee that the TOA discriminator threshold is crossed.

---

## 15.10 TOT values are missing

Check:

- TOT threshold;
- injected charge;
- TOT trim;
- analog configuration.

TOT generally requires a significantly larger signal than a simple ADC measurement.

---

## 15.11 Internal trigger works but external trigger does not

Check:

```text
[ ] Correct SMA connector
[ ] Ext Trg En enabled
[ ] Correct pulse amplitude
[ ] Correct DC offset
[ ] Correct pulse polarity
[ ] Correct pulse width
[ ] Trigger delay
[ ] Trigger dead time
```

Use an oscilloscope to confirm the actual voltage at the KCU105 input.

---

## 15.12 External trigger reaches KCU105 but RCDAQ records no events

Check the chain sequentially:

```text
External trigger
      ↓
FPGA accepts trigger?
      ↓
H2GCROC readout generated?
      ↓
UDP packet transmitted?
      ↓
DAQ PC receives UDP?
      ↓
RCDAQ plugin receives packet?
```

Use `tcpdump` to separate a network problem from an RCDAQ problem.

---

## 15.13 RCDAQ event rate is much lower than trigger-generator rate

Check:

- `nr_packets`;
- Machine Gun setting;
- external-trigger dead time;
- UDP packet loss;
- packet/event structure;
- RCDAQ device configuration.

The trigger frequency should not automatically be expected to equal the RCDAQ event frequency until the packet structure and RCDAQ event-building behavior are understood.

# 17. Quick Reference

For calibration:

```text
FPGA firmware
     ↓
Network check
     ↓
IOdelayY
     ↓
PedestalCalibY
     ↓
InjectionY
     ↓
TOA / TOT calibration
     ↓
InjectionDACY
     ↓
Save configuration
```

For normal data taking:

```text
H2GConfig
     ↓
H2GDAQ generator configuration
     ↓
rcdaq_server
     ↓
load H2GCROC plugin
     ↓
create_device
     ↓
daq_open
     ↓
daq_begin
     ↓
pmonitor / roc_analysis
```

The key idea is to keep the roles separated:

```text
H2GCalibX = determine calibration parameters
H2GConfig = write ASIC configuration
H2GDAQ    = configure FPGA generator
RCDAQ     = acquire and store event data
roc_analysis = decode and monitor event data
```
